# Staged latency `_ts` envelope — design

**Date:** 2026-05-29
**Status:** approved
**Repos:** `ros2-robot-fleet-demo` (this) + `ros2_kafka_dispatcher` (sinks)

## Problem

The latency pipeline records three timestamps per message: `t0` (dispatcher
publish, from `header.stamp`), `t1` (broker-ingress), `t2` (consumer receive).
`t1` is only available for Kafka (read from the broker `CreateTime`); for MQTT a
subscriber cannot observe broker-arrival time, so `t1` is null. We want a
uniform, broker-agnostic `t1` and an extensible structure so later system
components (consumer, ksqlDB / GIS4IoRT) can append `t2`, `t3`.

## Stage semantics (locked)

| Stage   | Meaning                          | Stamped by                       | Repo            |
|---------|----------------------------------|----------------------------------|-----------------|
| `t0_ns` | message generated by dispatcher  | `robot_replay.py` (`header.stamp`) | this (exists)  |
| `t1_ns` | message reaches broker (MQTT+Kafka) | sink at `publish()`/`produce()` | dispatcher (new)|
| `t2_ns` | consumed                         | consumer                         | this (exists)   |
| `t3_ns` | ingested downstream              | ksqlDB / GIS4IoRT                | future          |

## Transport: JSON `_ts` envelope

A top-level object added to the JSON payload. Each hop appends its stamp; the
envelope travels with the message.

```json
{
  "header": { "stamp": { "sec": 1779985112, "nanosec": 917221721 }, "frame_id": "robot_1" },
  "latitude": 52.23, "longitude": 16.24, "...": "...message fields...",
  "_ts": {
    "t0_ns": 1779985112917221721,
    "t1_ns": 1779985112918002310
  }
}
```

- **JSON payloads only.** CDR payloads cannot carry extra fields; their `t1`
  stays null (documented). The latency benchmarks use JSON.
- `t0_ns` is duplicated into `_ts` from `header.stamp` for a self-contained
  envelope; `header.stamp` remains the source of truth.

## Changes by component

### Dispatcher repo (`ros2_kafka_dispatcher`)

`mosquitto_bridge/mosquitto_sink/src/mosquitto_sink_node.cpp` and
`kafka_bridge/kafka_sink/src/kafka_sink_node.cpp` share a
`serialize_message_to_json(...)` free function. Extend it so that, after
`build_json_message`, it attaches an `_ts` object:

- `_ts.t0_ns` = `header.stamp.sec*1e9 + nanosec` read back from the built JSON
  (`payload["header"]["stamp"]`); omitted if absent/zero.
- `_ts.t1_ns` = wall-clock now in ns at serialization (immediately before
  publish), via `std::chrono::system_clock`.

CDR path untouched.

### This repo — `consumer/consume.py`

- New helper `_stages_from_json(payload) -> dict` returns the `_ts` object (or
  `{}`).
- `_decode(...)` returns `(t0_ns, t1_ns)`: `t0` prefers `_ts.t0_ns` then
  `header.stamp` (JSON) / CDR; `t1` is `_ts.t1_ns` or `None`.
- Kafka handler: `t1 = decoded t1` if present **else** Kafka `CreateTime`
  (backward compat). MQTT handler: `t1 = decoded t1` (now populated) else
  `None`.
- `t2_ns` set on receive as today; `_log_latency` unchanged.

### This repo — `tools/analyze_latency.py`

Already stage-aware (`ingest = t1−t0`, `transport = t2−t1`, tolerant of null
`t1`). No structural change — with MQTT `t1` populated, its `ingest`/`transport`
columns now light up. Update the "n/a for MQTT" wording in README.

## Backward compatibility

Old artifacts and CDR payloads have no `_ts`: `t0` falls back to `header.stamp`,
`t1` falls back to Kafka `CreateTime` (Kafka) or `None` (MQTT). `analyze`
already handles null `t1` and missing `t2`.

## Testing

- **Consumer (Python):** unit-test `_stages_from_json` and `_decode` returning
  `(t0, t1)` from a JSON payload with `_ts`; fallback when `_ts` absent (Kafka
  CreateTime path, MQTT None).
- **Analyzer:** existing tests cover stage math; add one asserting MQTT records
  carrying `t1` produce non-null `ingest`/`transport`.
- **Dispatcher (C++):** extend `test_mosquitto_sink.cpp` to assert the JSON
  output contains `_ts.t1_ns` (and `t0_ns`). Build with colcon if feasible;
  otherwise the image must be rebuilt to take effect at runtime.

## Out of scope

`t3_ns` (ksqlDB/GIS4IoRT ingestion) — the envelope is forward-compatible; that
component appends `t3` later.
